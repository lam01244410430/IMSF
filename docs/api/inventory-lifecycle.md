# Inventory lifecycle and expiry jobs — P05-01 Steps 2–3

All new P05 contracts and policies below are **PROPOSALS**, implemented for merge review under the approved Steps 2–3 scope. Passing tests do not decide OPEN items. P04 inventory writers, terminal states, FEFO ordering and the confirmed role matrix remain authoritative.

With `H = /api/v1/households/{household_id}`, Step 2 adds:

| Method/path | Response | Access |
|---|---|---|
| GET H/inventory/lifecycle | LifecyclePage | VIEW: OWNER, ADMIN, FINANCE_MANAGER, INVENTORY_MANAGER, MEMBER, VIEWER |
| GET H/expiration-alerts | ExpirationAlertPage | Same VIEW roles |
| GET H/expiration-alerts/{alert_id} | ExpirationAlertResponse | Same VIEW roles |

Each read revalidates ACTIVE user, live Bearer session and current membership through the existing household-access adapter. Archived households remain readable. Invisible household/path/filter/cursor IDs return 404 `INVENTORY_NOT_FOUND`. Step 3 adds the enqueue/status contracts below with existing permissions.

## Lifecycle evaluation

**PROPOSAL OPEN-01/07:** `days_left = expires_on - local_date`. More than three days is FRESH, zero through three is WARNING, negative is EXPIRED, and an undated lot is UNKNOWN with null days_left. These are derived on each read, never stored on lots. Each request samples the UTC clock once, converts to the explicitly configured household IANA timezone and shares that local date across all returned lots.

Missing, empty, non-string or invalid `household_settings.values["timezone"]` returns 422 `INVENTORY_TIMEZONE_REQUIRED`. There is no UTC, host, browser or settings-default fallback and no settings mutation. Household authorization and referenced-object scope checks precede this error.

`LifecyclePage` contains `items`, `next_cursor`, `local_date`, `timezone`. Each item contains lot_id, household_id, product_id, received_at, exact decimal-string received_quantity/remaining_quantity, expires_on, lot_archived_at, product_archived_at, household_archived_at, activity_state (ACTIVE for positive quantity, TERMINAL otherwise), the retained terminal_state, freshness, days_left, local_date and timezone. CONSUMED/DISCARDED/RETURNED/ADJUSTED_OUT/MIXED labels are never replaced by calendar freshness. Terminal and archived rows remain visible.

Optional filters: positive BIGINT product_id/lot_id and freshness (FRESH/WARNING/EXPIRED/UNKNOWN). A lot/product filter mismatch returns 404. The freshness predicate is applied before SQL LIMIT. Pages ascend by lot ID, default to 50 and accept 1–200. Cursors bind household, filters and evaluation date/timezone. Foreign scope/position returns 404, mismatched filters or malformed cursor returns 422 `INVENTORY_INVALID_INPUT`, and a stale date/timezone returns 409 `INVENTORY_STATE_CONFLICT`. Restart pagination after a conflict. Cursors describe live reads, not a frozen stock snapshot.

**PROPOSAL OPEN-01/03:** only positive, dated, nonterminal, unarchived lots of unarchived products in active households qualify for NEW alerts. The Step 3 producer applies the same pure eligibility predicate.

## Historical alerts

**PROPOSAL OPEN-02/03/07:** pages contain `items` and `next_cursor`, ascending by alert ID, default 50, maximum 200. Optional filters are scoped lot_id, kind (WARNING/EXPIRED), inclusive local_date_from/local_date_to. An inverted range returns 422. Cursors bind household and filters. Detail and list responses expose only id, household_id, lot_id, alert_kind, local_date, created_at, expires_on_snapshot, timezone and job_id. Job IDs are provenance, not authorization to a job administration API. There is no lease token, internal payload, checkpoint, exception or credential in a response.

Historical reads do not require a currently valid timezone: observed date, expiry and timezone are immutable provenance. Later expiry edits, consumption, disposal, archive or timezone changes do not rewrite alerts. Standing household records are the proposed in-app data contract only; there is no email, recipient inbox, read state or frontend notification center in Step 2.

## Persistence and downgrade

**PROPOSAL OPEN-02/10:** revision 8 follows revision 7. Alerts have scoped lot/job composite RESTRICT foreign keys and unique `(household_id,lot_id,alert_kind,local_date)`. Runtime SELECT/INSERT only, with database UPDATE/DELETE/TRUNCATE history guards. Job scope/key/kind/original run_after/payload/created_at are immutable. Column-scoped updates permit only state, attempt_count, lease_until, lease_token, completed_at, error_code, checkpoint and result. DELETE/TRUNCATE are prohibited. No cascade removes history.

Downgrade locks both new relations in ACCESS EXCLUSIVE mode before checking history. Any job or alert (including terminal work) refuses with SQLSTATE 55000. The transaction leaves schema, rows and grants intact. Empty-only downgrade drops revision-8 objects and the additive expiry index, retaining every revision-7 row. Owner-controlled function metadata records source SELECT grants added by revision 8; downgrade removes only these additions and preserves pre-existing worker read grants. Revisions 1–7 are frozen.

**PROPOSAL OPEN-04/05/08, DDL only:** job_key is an opaque nonempty string of at most 200 characters, scoped uniquely to a household. Kind is INVENTORY_EXPIRY. The four stored states are READY/RUNNING/SUCCEEDED/FAILED, attempt_count is nonnegative, RUNNING requires paired nonempty lease_token/lease_until, other states have neither; terminal states require completed_at. New rows start READY with zero attempts and empty versioned progress/result. Terminal outcomes are immutable. These storage guards do not implement claim or lease fencing.

Payload, checkpoint and result are JSONB objects, at most 4096 UTF-8 bytes each with numeric `schema_version: 1`. Payload requires exactly local_date (valid ISO calendar date) and timezone (validated timezone name). Checkpoint allows optional nonnegative BIGINT high_water_id/last_lot_id. Result allows optional nonnegative BIGINT scanned_count/warning_count/expired_count and a bounded uppercase outcome_code; Step 3 outcome-code meanings are specified below. Unknown keys are rejected. Error codes and lease tokens have bounded storage. This server-owned payload has no public input route.

Step 3 implements the following behavior as **PROPOSALS** for merge review. The storage shapes and revisions 1–8 remain frozen.

## Expiry run API — PROPOSAL OPEN-07

| Method/path | Request/response | Access |
|---|---|---|
| POST H/inventory/expiry-runs | Required `{}` + Idempotency-Key → 202 ExpiryRunResponse | INVENTORY_MANAGE: OWNER / INVENTORY_MANAGER only |
| GET H/inventory/expiry-runs/{job_id} | 200 ExpiryRunResponse | VIEW: all six confirmed roles |

The POST enqueues/reuses the canonical current-local-day job; it does not process inventory synchronously. No caller date/timezone/kind/state/household/actor overrides are accepted. Missing/invalid timezone returns 422 `INVENTORY_TIMEZONE_REQUIRED`, without a job or successful transport reservation. Extras and malformed/missing keys return 422 under the existing inventory route validation. Keys use the existing printable ASCII (1–128) validation, canonical request digest, transactional reservation and saved response protocol. **Additional frozen-schema PROPOSAL:** revision 4 only permits persisted idempotency statuses 200/201/204. Enqueue stores the exact response body with internal status 200 using the existing reservation/completion protocol; this endpoint maps both initial and saved success to HTTP 202. A literal persisted 202 would require a separately approved new migration. Merge review must confirm this endpoint-specific encoding. Current identity/session/membership/MANAGE and active-household checks run before replay. Different transport keys converge on one daily job. Replay with the original key returns the originally saved 202 body, which can still say READY after completion; use GET for current state. Archived-household replay is refused, reads remain available. Foreign job IDs return 404 without leaking existence.

ExpiryRunResponse explicitly allows only id, kind, captured local_date/timezone, state, attempt_count, run_after, completed_at, scanned_count, warning_count, expired_count, error_code and outcome_code. Counts are nonnegative BIGINT-bounded values; attempts use the database INTEGER bound. No lease token/expiry, checkpoint, arbitrary payload, credentials, raw exception or audit contents are returned. Warning/expired counts count alerts actually inserted by this job; scanned_count counts every observed source lot, including ineligible lots.

## Worker protocol and frozen-DDL resolutions — PROPOSALS

**OPEN-03:** standing household alerts are the in-app record only. No recipient inbox, email, read marker or frontend delivery is added. A WARNING or EXPIRED event retains observed expiry, date, timezone and job_id. INSERT ON CONFLICT uses `(household_id,lot_id,alert_kind,local_date)`; the database is the deduplication authority.

**OPEN-04:** canonical `inventory-expiry:v1:{local_date}` is unique within each household. The proposed dispatcher cadence is 15 minutes; no scheduler is deployed. One invocation reads at most 100 active household IDs in ascending order, after an explicit high-water pagination position, and handles each household in its own transaction. Call the next page using last_household_id until an empty page. Reset the position on the next dispatch cycle. Only the current local day is enqueued; a completed daily job never reruns. Diagnostics contain household_id and stable error_code only.

**READY → terminal decision — PROPOSAL, merge gate confirms:** every skip claims first: READY → RUNNING → SUCCEEDED with SKIPPED_STALE or SKIPPED_ARCHIVED. Revision 8's guard explicitly allows READY → READY/RUNNING only; it also forbids every terminal update. Revision 8 is frozen. A direct never-claimed READY → terminal path would require a **NEW migration**; it is not implemented here.

**OPEN-05:** claim uses a short jobs-only FOR UPDATE SKIP LOCKED transaction, selecting due READY work or expired RUNNING leases. It issues a fresh random token, increments attempt_count and commits before source/effect work. Claiming alone inserts no alert and changes no inventory. Effects lock household first, then job, and validate the matching unexpired token using database clock_timestamp. A final conditional UPDATE checks that token/time again after inserts. Zero updated rows raises LeaseLost and rolls back the entire batch. Successful unfinished batches renew the lease to DB time + 60 seconds in that fenced UPDATE. Never acquire the household lock while retaining a claim transaction's job lock.

**Trap (a), PROPOSAL:** run_after is guard-frozen and cannot carry retry delays. On a handled failure, the job stays RUNNING with a replacement random token that invalidates the prior owner; lease_until becomes DB time + 60 seconds after claim 1 or +300 seconds after claim 2. It serves as the reclaim not-before marker. This satisfies the RUNNING-only paired-lease constraint. No worker receives the replacement token. The next claim is allowed only after expiry. Claim 3 failing is terminal FAILED. A process dying during claim 3 becomes terminal FAILED when due discovery next locks that expired lease; there is no fourth claim. The original run_after stays unchanged. A RUNNING response with an error_code can therefore mean retry wait; it is not a delivery SLA.

The batch retries whole rolled-back transactions up to three times for the existing inventory transient classification (40001, 40P01, 57P01, class 08 or invalidated connection). This transaction budget is separate from the three-claim job budget. `work()` records `INVENTORY_RETRY_EXHAUSTED` for exhausted transient faults, `INVENTORY_TIMEZONE_REQUIRED` for invalid current settings, or the new **PROPOSAL** `INVENTORY_EXPIRY_FAILED` for other handled failures. No raw exception is persisted. If failure recording itself cannot commit (database unavailable or lease lost), the lease expires and a new claimant recovers. A stale owner cannot record a failure or complete effects.

**Trap (b), PROPOSAL:** the frozen payload validator requires exactly schema_version/local_date/timezone and a valid IANA zone. An invalid household cannot receive a new job row. Dispatch returns a sanitized per-household `INVENTORY_TIMEZONE_REQUIRED` diagnostic and proceeds to other households. It never invents a timezone or inserts an invalid-payload failure row. An already-enqueued job whose current timezone becomes invalid records that code via the handled-failure path, without new alerts.

**Trap (c), PROPOSAL OPEN-10 limitation:** revision 8 contains only timezone_valid/payload_valid/progress_valid/guard_job; no inventory_expiry_lock_household() exists. The implementation reuses the household FOR UPDATE lock used by inventory's identity-compatible access adapter. System execution has no user/member prefix and fabricates no actor/session. The SELECT-only dedicated worker role cannot acquire this lock: PostgreSQL also requires UPDATE privilege. **Least-privilege production execution remains blocked on OPEN-10**; tests execute orchestration with the existing disposable runtime identity, distinct from the migrator, and retain the dedicated worker's denial of stock/finance writes. No helper, new migration, business grant or production credential is created here. Do not deploy a broadly privileged runtime worker as a substitute for that review.

**Trap (d), PROPOSAL:** every completion atomically sets terminal state, completed_at and both lease columns NULL, including empty runs, final batches, skips, handled failure 3 and expired claim 3. Terminal rows are never edited; lost acknowledgements replay their sanitized persisted summary.

**Trap (e), PROPOSAL:** checkpoint uses only schema_version/high_water_id/last_lot_id; result uses only schema_version/scanned_count/warning_count/expired_count/outcome_code. Codes COMPLETED, SKIPPED_STALE and SKIPPED_ARCHIVED fit `^[A-Z][A-Z0-9_]{0,63}$`. No new JSON keys or DDL are added.

**OPEN-06:** each effect transaction resolves the validated household timezone and samples the evaluation clock once. A captured date/timezone mismatch skips the claimed job with SKIPPED_STALE and no further alerts. If the date differs, it also enqueues/reuses the actual current-day job within the same fenced transaction. Timezone-only drift with the same local day retains the skipped result without looping on the unique key. Archived households receive SKIPPED_ARCHIVED, no new effects. Retain previously committed batches. No historical backfill or rerun after SUCCEEDED; receipts/expiry edits after scanning appear in live lifecycle reads immediately and in the next local-day job. This accepts up to one local-day alert delay. Same-day generations/correction/backfill remain alternatives, not implemented.

**OPEN-08:** first effect batch captures the household's source-lot high-water ID. Pages contain at most 100 lots in ascending ID, after last_lot_id and at or below high_water_id. Each batch observes committed state while serialized against application inventory/settings writers. It does not promise a stable lifetime inventory snapshot or serialize arbitrary out-of-protocol SQL writers. New higher-ID receipts and edits behind the checkpoint wait for the next local day. Scan eligibility excludes undated, zero, terminal, archived-lot/product/household stock. Final page completion and its alerts/checkpoint/result commit together. On failure, this batch rolls back; **earlier committed batches may remain**, identified by job_id. A batched job is not all-or-nothing across its lifetime.

## Worker run and recovery — PROPOSAL OPEN-10

No command is installed, scheduler started, production secret provisioned or public job administration added. In a reviewed system host, construct `ExpiryJobs(async_session_factory)` from `app.lifecycle.jobs`; callers supply the execution identity explicitly. Use `await jobs.dispatch(after_id=..., limit=100)` for each bounded page, then `claim = await jobs.claim()` and, if non-null, `await jobs.work(claim)`. A claim commits before work begins. Hosts must handle LeaseLost by discarding ownership and observing persisted status; they must not force a stale completion. The next cadence discovers eligible expired leases. Avoid holding application transactions around these methods. `batch(claim)` is the bounded transactional primitive; `work(claim)` processes that attempt until terminal or handled failure. This is an application interface, not production provisioning approval.

Operators inspect sanitized GET status and dispatcher diagnostics, correct invalid settings through authorized household commands, and allow the delayed lease reclaim. Failed jobs retain earlier batches, counters, provenance and stable error code. SUCCEEDED/FAILED daily jobs are immutable; no retry/reset/reopen endpoint or SQL guard bypass is provided. A terminal failure requires operator review; after correcting the underlying cause, the next local-day job can proceed. Same-day terminal recovery would need a separately approved generation/storage policy; do not change run_after/payload/state or delete history to retry it. Production credential choice, narrow lock capability, supervisor/concurrency limits, audit/log sink, executable packaging, operator alerting and terminal same-day recovery remain deferred by name under OPEN-10/05.

## Privilege provisioning remains open

**PROPOSAL OPEN-10:** migration requires explicit existing `FINANCE_RUNTIME_ROLE` and distinct `INVENTORY_EXPIRY_WORKER_ROLE`. Both must be unprivileged, separate from migration ownership, with no public schema CREATE. The worker must have no role memberships (including NOINHERIT SET ROLE paths) or effective table/column write privileges on any existing business relation; preflight refuses such configuration before DDL. No production credentials are created.

Migration grants SELECT/INSERT and sequence USAGE/SELECT on new relations, controlled job UPDATE columns to both roles, and household/settings/product/lot SELECT to the worker. Validation functions have PUBLIC execution revoked and only the required roles receive EXECUTE. Household SELECT alone does not grant FOR UPDATE. Exact production provisioning and a narrow household-lock capability remain OPEN-10; Step 3 application invocation and recovery semantics are above. The dedicated SELECT-only worker remains unable to run effects safely until this is separately resolved.

Disposable verification uses the existing p02_test_* / p03_finance_test_* guarded fixtures, separate migrator/runtime credentials, and explicit INVENTORY_EXPIRY_WORKER_DATABASE_URL for the actual worker-credential grant probe on that same disposable finance DB. Revision-8 rehearsals require a separate fresh p05_rehearsal_test_* database with EXPIRY_REHEARSAL_DATABASE_URL and matching P05_REHEARSAL_DATABASE. Source-schema USAGE is an operator prerequisite for the configured roles. No history DELETE cleanup or development/production database is used. Remote CI is not established by local tests.
